# Ethos 行为验证

这些场景检验 Agent 是否能发现、积累、整合并应用项目判断。它们不是已经执行的测试结果，也不是仅搜索 Skill 中的关键词就能通过的结构测试。

## 执行方式

1. 为每个场景创建独立临时 Git 仓库，写入 `scenarios.json` 的 `base_files`，再应用该场景的 `setup`。记录源码提交、实际加载的 Skill 路径与版本、模型、日期、权限及确认没有残留 Ethos Hook 的证据。只启用一份 Ethos；除可选交接场景外不安装 Loop。
2. 通过真实用户入口提交各 session 的 `prompt`。将 `input_files` 作为场景输入写入临时仓库；不要把 `checks`、其他场景或本执行指南交给被测 Agent。自动发现用例不能额外提示“请学习”、显式调用 `$ethos`，或注入预期结论。
3. 每个 session 使用全新的会话或进程，不继承上一个会话的消息、总结、隐藏记忆和评判结果。仅保留同一场景的工作区文件。这样才能证明跨会话积累来自磁盘证据。
4. 保存完整用户输入、Agent 回答、工具轨迹与回合事件（包括任何 `hook_prompt` 或结束后的续跑），以及每轮前后的文件树和差异。必须包含被 Git 忽略的 `.proj-ethos/.local/`；仅看 `git diff` 会遗漏候选状态。只读场景比较整个工作区的内容哈希和路径集合。
5. 由另一个审阅者按语义逐条判断 `checks`，附上回答、文件或工具轨迹证据。结论使用“通过 / 失败 / 未执行 / 环境阻塞”。缺少工具轨迹时，不能仅凭最终回答认定读取、写入或去重确实发生。

`setup` 中的自然语言操作由测试主持人在开始前执行，不能作为附加指令发给被测 Agent。候选夹具应遵循当前版本的候选格式；从已验证的真实候选生成夹具，保留来源的独立性，不用重复复制伪造支持度。期限、候选上限和单条证据上限取自被测版本的 [candidates.md](../plugins/ethos/skills/ethos/references/candidates.md)，并在报告中记下实际值，不在场景中另立常量。生命周期边界应分别覆盖刚好达到期限、刚过期、未过期、写满容量后追加独立候选和已有记录超出容量；固定本轮测试日期，避免运行日期漂移。明确拒绝的候选按该文件保留简短有期限的拒绝记录，检查它不会被同一证据反复激活。

## 入口与结论边界

无额外续跑是独立验收条件：一次用户提交应在正常回答后结束，不应由 Ethos 新增反馈消息或学习专用回合。Skill 被实际选择时仍会进入上下文；这里禁止的是每轮额外注入和强制续跑，不将隐式技能描述宣称为零上下文开销。

- 首先用安装后的 Skill 跑隐式选择与自动发现，不显式调用 `$ethos`，也不注入每轮学习提示。若环境不能加载插件，只能明确标为“直接加载 Skill 的能力验证”，不能声称验证了自动入口。
- 最小回归运行所有场景一次；发布验证对关键的自动发现、跨会话、只读场景各运行至少三次。报告每次结果与失败样本，不仅报告成功率。普通任务的无额外续跑场景也必须通过宿主真实入口执行。
- 测试前先核实测试模型看不到此评判文件。若它已读过评判标准，另开无继承上下文的被测会话；否则本次只能算演练。
- 不强制最终知识的字面措辞、标题或文件总数。检查适用条件、理由、反例、权威归属、旧规则替换和副作用；正确地没有写入同样是成功。
- 候选不是项目原则。可读取候选用于判断是否需要进一步证据，但不能将它作为权威直接改变产品选择。自动写入明确原则不要求额外确认；模型推断的重大方向变更仍需澄清。
- 记录行为通过不能证明未来所有会话都可靠。仓库结构校验通过也不能证明任何行为场景通过。

建议每次执行保留一个独立报告：环境信息、场景与 session 标识、各检查结论、证据路径、失败原因、重跑结果。运行日志和临时仓库保存在仓库外，不纳入插件发布内容。
