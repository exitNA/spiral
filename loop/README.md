# `$loop` — “说需求即可”的自主开发 Skill

这个 Skill 的目标是让用户只描述**想要的结果**，不需要先学会怎么给 Coding Agent 写一份面面俱到的 Prompt。

最典型的使用方式：

```text
$loop 给登录页加上记住密码
```

也可以很短：

```text
$loop 把这个页面做成响应式
$loop 修复上传大文件失败的问题
$loop 增加用户导出功能
$loop 按照 PRD 完成开发
```

`$loop` 本身就代表：**Skill 接管完整的软件开发执行过程。**

用户不需要再补充：

```text
请分析代码
请拆任务
请使用多 Agent
请写测试
请 Review
失败后继续修
不断循环
直到 100% 有信心
```

这些都属于 Skill 的内部职责。

## 核心行为

### 1. 短需求自动扩展

如果用户只说一句需求，`$loop` 会优先从以下信息中补齐细节：

```text
用户要求
  ↓
AGENTS.md
  ↓
PRD / 设计 / issue（如果存在）
  ↓
现有测试和当前行为
  ↓
项目架构 / API / UI 模式 / CI 约定
  ↓
相邻功能
  ↓
框架惯例
  ↓
保守、可逆的默认选择
```

内部会形成一个轻量的 `Intent Spec`，包含目标、范围、验收标准、兼容要求、风险和必要假设，但**不要求用户自己写出来**。

### 2. 尽量不反问

能从代码库推断的，不问。

小的、可逆的产品细节有合理默认值的，不问。

只有下面这种真正影响产品方向或安全边界的问题才问：

- 两种业务规则都合理，项目中没有依据；
- 不同选择会改变外部 API/数据语义；
- 涉及不可逆数据迁移；
- 需要生产权限、凭据、付费、部署等外部授权。

即使需要问，也只问阻塞当前工作的最小问题，而不是让用户重新补一份 PRD。

## 3. 先判断项目阶段，再决定是否兼容

`$loop` 不用“仓库代码有多少、历史有多久”判断项目是否成熟。

真正的判断标准是：**是否已经实际部署到生产环境，并形成真实用户、外部消费者或持久化状态依赖。**

```text
没有真正上线生产
→ 即使代码很多，也属于新项目
→ 优先做当前最合理、最干净的实现
→ 不为旧的内部实现保留兼容层

已经上线生产
→ 识别真实 API / 数据 / 客户端 / 用户行为兼容要求
→ 有计划地兼容或迁移
```

数据库是例外：**已经执行过的 migration 属于历史状态。** 后续修改必须从最新已应用状态继续演进，不能因为项目仍处于开发阶段就随意改掉已执行的 migration。

这可以避免新项目中出现大量没有真实价值的：

- compatibility adapter；
- legacy fallback；
- old/new 双实现；
- deprecated internal API；
- 无意义的数据格式兼容；
- 为早期错误设计继续背负的冗余代码。

## 4. 快速迭代：像画画一样从整体到局部

`$loop` 的快速迭代不是“快速把一个局部做精细”，而是**从粗糙整体逐步收敛到精细局部**：

```text
整体草图
  ↓
粗粒度但真实可运行的整体
  ↓
验证架构 / 主链路 / 产品方向
  ↓
修正方向
  ↓
完善主要功能
  ↓
边界 / 异常 / 性能 / UI 细节
  ↓
最终精修
```

就像画画：先确认构图、比例和大的形体正确，再画五官、纹理和光影。

开发中同样不要在整体方向尚未验证时，长时间深入某一个模块、组件、页面或局部算法。否则实施一段时间后才发现架构、接口或产品方向错误，会造成大量返工。

第一轮更关注：

- 整体架构和主要模块是否合理；
- 主用户流 / 数据流 / 控制流是否完整；
- 主要接口和数据模型是否能自然连接；
- 应用/服务能否真实启动；
- 核心端到端路径是否能跑通；
- 最大技术风险是否已经得到验证。

随后再逐层细化：

```text
主要正确性
→ 数据完整性 / 安全 / 并发 / 错误处理
→ 重要边界和集成
→ 性能和资源
→ UI 状态 / 可访问性 / 响应式 / 视觉
→ 低风险精修
```

“粗糙整体”也不是 Demo 或临时代码。第一版整体仍然应该使用准备长期保留的生产级技术方向，只是暂时不把每个局部做到极致。

## 5. 默认技术与工程规范

当项目没有既定技术约束时，优先选择当前工业界成熟、活跃维护、适合长期生产的方案，而不是最容易写 Demo 的方案。默认偏好：

- 单平台桌面：原生语言 + 原生框架；
- 跨平台桌面：优先 Rust 中心方案；
- Web/网络后端服务：优先 Go；
- AI/ML：优先 Python + `uv`；
- 前端：优先 TypeScript + `pnpm`；
- 数据库访问：优先成熟 ORM / query framework；
- 多个长期技术栈都合理且影响重大时，可以给出推荐并让用户选择。

所有可执行应用/服务默认要有日志：

```text
控制台日志：人类可读 + 默认颜色高亮
文本日志：人类可读 + 不包含 ANSI/颜色控制符
```

同时应有合理的日志轮转/保留策略，且不能记录密码、Token、私钥等秘密信息。

UI 默认遵循当前主流产品设计与可访问性方向，不使用明显守旧、过时的视觉和交互作为“安全默认值”。

## 6. `$loop` 自动完成整个开发过程

内部执行模型大致是：

```text
理解意图
   ↓
补齐需求与验收标准
   ↓
分析代码与依赖
   ↓
任务图 / 并行边界
   ↓
多 Agent 或单 Agent 执行
   ↓
集成
   ↓
测试 / Review / 运行验证
   ↓
发现问题 → 修复并调整策略
   ↓
客观质量门禁通过
   ↓
完成
```

这个过程是 `$loop` 的内部控制逻辑，不需要用户在 Prompt 里显式写“不断循环”。

## 7. 不使用“100% 自信”作为停止条件

`$loop` 判断完成依赖的是**证据**，而不是模型主观说“我有信心”。

默认会关注：

- 用户要求是否真正实现；
- build/type/lint/static checks；
- 相关现有测试；
- 新行为的 targeted/regression tests；
- 并行开发后的最终集成验证；
- 独立 Reviewer；
- 适用时的 E2E / 浏览器 / runtime 验证；
- 是否有高严重度 correctness/security/data-loss/compatibility 问题；
- 是否意外修改了无关代码。

所以不需要用户写类似：

> 你对当前实现 100% 有信心吗？如果没有就继续循环……

这种 Prompt。

## 8. 多 Agent 是自动调度能力，不是用户参数

主线程充当 Orchestrator，负责：

- 用户意图；
- 内部需求与验收标准；
- Task DAG；
- Critical Path；
- Agent 分工；
- 代码集成；
- 时间和效率；
- 质量门禁。

适合并行的探索、Review、测试和低冲突实现会自动分配给子 Agent。

写代码的并发数量不会固定：冲突/返工升高就减少，并行收益明显时才增加。

## 9. 时间和效率反馈

`scripts/loop_runtime.py` 可以记录：

- 总 wall-clock time；
- discovery / implementation / integration / verification / repair 等阶段耗时；
- Agent / Task 耗时；
- 首轮成功率；
- 返工；
- 冲突；
- verification failures；
- review defects；
- 并行效率和阻塞。

运行中如果发现：

```text
Agent 太多 → 协调成本高
```

后续任务就减少并发并扩大任务粒度。

如果发现：

```text
任务太大 → 返工率高
```

后续就缩小任务、加强验收标准和测试前置。

所以 `$loop` 优化的是**完成质量和真实 wall-clock 效率**，而不是 Agent 数量。

## 10. 跨运行学习

运行数据默认保存在：

```text
$CODEX_HOME/loop-runtime/
```

未设置 `CODEX_HOME` 时：

```text
~/.codex/loop-runtime/
```

它会把重复出现的过程问题压缩成项目级经验，例如：

```text
src/core 不适合多个 Worker 并发修改
先生成 API types 再并行 UI 任务
全量集成测试很慢，单任务先跑 package targeted tests
```

下一次 `$loop` 直接作为调度提示使用，而不是把全部历史对话塞回上下文。

## 11. 项目自进化与跨会话恢复

开发的各轮次同时执行：

```text
Observe → Orient → Hypothesize → Act → Verify
→ Record → Generalize → Compress → Decide
```

保留原版从整体到局部的开发节奏。每轮的反馈先形成可验证证据，再沉淀为测试、契约、工具或执行经验。涉及项目心智、品味、领域理解、协作原则和重要取舍时，由 `$ethos` 整合到已有项目知识体系。

默认按 Goal 模式完成开发；Turn 用于人控制方向的实验，Time/Event 用于明确授权的定时或事件执行，Continual learning 用于持续吸收真实反馈并验证历史能力。技能本身不创建后台任务。

跨会话任务可使用 `templates/LOOP.md` 和 `templates/STATE.md` 保存任务契约和恢复快照。运行脚本负责过程统计，模板负责下一次能够继续工作，两者不能互相替代。

Loop 与 Ethos 是两个独立插件。通过当前技能目录发现可用的 Ethos 后，Loop 可以使用它沉淀项目心智；Ethos 也会在普通对话和开发过程中自动识别并整合高置信学习。未安装 Ethos 时，Loop 正常完成开发与验证，不产生待整合任务，也不要求安装。

## 目录

- `SKILL.md`：完整开发执行契约及学习循环入口。
- `agents/openai.yaml`：显式 `$loop` 调用设置。
- `assets/agents/`：架构、测试和独立审查角色模板。
- `scripts/loop_runtime.py`：原版运行统计与跨运行过程提示。
- `references/`：需求展开、项目阶段、工程规范、编排、验证、效率、学习与压缩规则。
- `templates/`：任务契约和恢复快照。

本版以找回的 `loop-bak/` 为基础，合入此前重建的学习和 Ethos 协作能力。详细来源见 [合并依据](references/sources.md)。

## 安装独立插件

从 Spiral 仓库根目录注册 marketplace，再安装 Loop：

```bash
codex plugin marketplace add /path/to/spiral
codex plugin add loop@spiral
```

需要自动沉淀项目心智时，可另外安装 `ethos@spiral`。安装后启动新任务以加载插件。

```text
$loop <我想完成的需求>
```
