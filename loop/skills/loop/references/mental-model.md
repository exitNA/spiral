# Execution and learning

## What learns

Treat the software system as the learning substrate: implementation, rules, tools, state representations, tests, replay cases, memory, and the mechanism that updates them. Select the artifact whose change prevents recurrence or improves a future decision.

A successful retry solves an instance. A reproducible case plus a validated system change can improve a class of future outcomes. A new prose rule is justified only when the lesson cannot be expressed better in an executable artifact or an existing authority.

## Two coupled loops

- **Inner execution:** investigate, act, verify, repair, deliver. Loop owns this workflow and its process improvements.
- **Project evolution:** reconcile feedback into the project's current mind, taste, and decisions. Ethos owns this coherent judgment system.

Mind explains what the project is and how it works. Taste supplies the project's quality bar. Decisions preserve important choices and their rationale. These inform one another rather than forming independent note collections.

Human feedback has scope. “Use this style in this experiment” is a local constraint; “This product should always make this tradeoff” can establish a durable principle. Preserve explicit scope. For an inferred consequential shift, show the old judgment, new evidence, and material difference before canonization. Previously established authorization does not need to be requested again.

## The human outer loop

Set constraints and acceptance criteria before autonomous execution. Use human sampling and audit where verifiers cannot capture quality, and retain human control over consequential architecture/product direction and production acceptance.

Escalation should present evidence and a concrete choice. Routine details should be resolved from established project judgment and repository conventions.

## Absorption and compression

Absorption turns useful feedback into a better system. Compression keeps the accumulated learning coherent and affordable to retrieve. Perform both: endless accumulation of patches and rules creates coupling and obscures the current model.

When exceptions multiply, reconsider the representation or abstraction they surround. Prefer a simpler model that explains the cases over another special case. Verify that compression preserves important distinctions and prior capabilities.
